# 보고서 디자인 가이드

`report-writer`가 작성하는 문서(`작업기록\*.md`)와, 그중 팀 공유용으로 렌더링하는 HTML 버전에 공통으로 적용하는 시각 규약이다. **md가 원본(진실)이고 HTML은 파생물**이다 — 이 순서를 뒤집지 않는다.

출처: [Urban Institute Data Visualization Style Guide](https://urbaninstitute.github.io/graphics-styleguide/)(색상·타이포·접근성), [FT Visual Vocabulary](https://github.com/Financial-Times/chart-doctor/tree/main/visual-vocabulary)(차트 선택), [Pretendard](https://github.com/orioncactus/pretendard)(한글 웹폰트).

## 1. 색상 팔레트

Urban Institute 핵심 8색(코어→보조 순 위계). md 문서에서는 색 자체를 못 쓰니 **상태 표시 텍스트 태그**로 옮겨 쓴다. HTML 렌더링에서는 아래 hex를 그대로 CSS 변수로 쓴다.

| 색 | hex | md 상태 태그로 매핑 |
|---|---|---|
| blue | `#1696d2` | `[정보]` — 참고용 사실 |
| green | `#55b748` | `[완료]` — 검증까지 끝남 |
| yellow | `#fdbf11` | `[미검증]` — 확인 안 됨, 추정 아님 |
| red | `#db2b27` | `[실패]` / `[블로커]` |
| gray | `#d2d2d2` | `[선재]` — Snap 원본 동일, 손대지 말 것 |
| orange | `#e66600` | `[주의]` — 부수작업 필요 |
| magenta | `#ec008b` | (문서에선 미사용 — 차트 전용 보조색) |
| space-gray | `#332d2f` | 본문 텍스트 색(HTML 기본 글자색) |

각 색은 9단계 tint/shade(`-1`=가장 밝음 ~ `-9`=가장 어두움)를 갖는다. sequential 차트(예: 배치 처리량 추이)에는 한 색의 단계만, categorical(예: 8개 프로젝트 비교)에는 core 8색만, diverging(예: 증가/감소)에는 두 색을 대칭으로 쓴다.

**규칙**
- **성별 등 이분 데이터에 blue=남/pink=여 같은 관습색 금지**(Urban 가이드 명시 경고) — yellow/cyan 등 무관한 조합 사용.
- **색만으로 상태를 구분하지 않는다.** 위 표처럼 항상 텍스트 태그를 같이 쓴다(색맹 접근성 + md에서도 동일하게 읽히게).
- HTML 렌더링의 배경색-글자색 조합은 WCAG AA(본문 18px 이하 기준) 충족하는 쌍만 쓴다 — 밝은 배경(`-1`~`-3`)엔 검은 글자, 어두운 배경(`-6`~`-9`)엔 흰 글자.

## 2. 타이포그래피

- **HTML 렌더링 폰트: Pretendard 고정.** `template.html`에 이미 CDN(`https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/static/pretendard.min.css`, `font-family: 'Pretendard'`)으로 박아둠 — 문서마다 다시 넣지 않는다. 폴백은 `-apple-system, BlinkMacSystemFont, system-ui, "Malgun Gothic", sans-serif`.
- md 문서는 폰트를 지정할 수 없다(뷰어가 결정) — 대신 **헤더 계층을 얕게**(H1 제목 1개, H2 섹션, H3까지만) 유지해 어떤 뷰어에서도 구조가 읽히게 한다.
- 본문 대비 제목은 굵기로만 구분(마크다운 `#`/`##`가 이미 이 역할), 별도 색상 강조는 HTML에서만.

## 3. 표(table) 규약

- 표 셀은 코드/식별자 나열이 아니라 **문장 조각**으로 쓴다(SKILL.md 규칙 7과 같은 원칙).
- 숫자 열은 우측 정렬(HTML `text-align:right`; md는 헤더 구분선 `---:`로 표시).
- 헤더 행은 굵게 + 위 색상표의 배경(옅은 tint, 예 `blue-1 #cfe8f3`)으로 강조 — HTML만.
- **짧은 라벨/상태칩 칸이 옆의 긴 칸에 밀려 글자 단위로 줄바꿈되는 문제** [검증 2026-09-22 · 내장브라우저 실측]: `class="key"`(짧은 항목명 칸)·`class="status"`(상태 태그만 있는 칸)를 `<th>`/`<td>`에 준다. `template.html`에 `width:1%+white-space:nowrap` 트릭으로 이미 정의돼 있다 — 내용이 실제로 짧은 칸에만 쓴다(긴 서술형 항목명 칸엔 쓰지 않는다, 그 칸은 강제로 안 줄어들면 오히려 다른 칸을 짜부러뜨린다).

## 4. 차트가 필요할 때 — 어떤 차트를 쓸지 (FT Visual Vocabulary)

작업기록 문서는 대부분 텍스트+표로 충분하고 차트는 드물게 필요하다(배치 처리량 추이, 8개 프로젝트 결함 수 비교 등). 필요해지면 "무엇을 보여주려는가"부터 정하고 아래에서 고른다 — 차트를 먼저 고르고 데이터를 끼워맞추지 않는다.

| 보여줄 것 | 추천 차트 | 이 프로젝트에서 나올 수 있는 예 |
|---|---|---|
| 시간에 따른 변화 | 라인(line) — 시리즈 1개, 불규칙 데이터면 마커 추가 | 배치 처리 건수 추이 |
| 크기 비교(절대값) | 컬럼/바(column/bar) — 축은 반드시 0부터 | 프로젝트별 결함 발견 수 |
| 순위 | 정렬된 바(ordered bar) | 프로젝트별 미검증 항목 수 순위 |
| 전체 대비 구성 | 누적 바(stacked column) — 구성요소 많으면 피하기 | 결함 심각도별(Blocker/Major/Minor) 비율 |
| 편차(+/-) | 발산형 바(diverging bar) | 예상 대비 지연/단축 |
| 분포 | 히스토그램 | (해당 사례 거의 없음) |

**금지**: 파이차트(구성요소 3개 넘으면 크기 비교가 부정확해짐 — Urban·FT 둘 다 경고), 이중 y축(오해 유발), 0부터 시작하지 않는 막대 y축.

## 5. 접근성

- 색만으로 의미 전달 금지(§1 규칙과 동일 — 항상 텍스트 라벨 동반).
- HTML 렌더링 시 배경-글자 대비 WCAG AA 이상.
- 표·이미지에 대체 텍스트/캡션 — 스크린리더·검색 모두 고려.

## 6. 레이아웃 패턴 (Toss Payments 개발자문서 참고, v2)

`docs.tosspayments.com/reference`를 Playwright로 직접 열어 관찰(추측 아님). 3단 레이아웃(좌 nav / 중앙 본문 / 우 다크 코드패널)을 우리 단일 정적 HTML 보고서에 맞게 옮긴 것:

- **엔드포인트 블록 패턴** → **Task/섹션 블록**: 배지(작은 pill, 예 `TASK 1`) + 제목 + 한 줄 설명, 그 아래 "필드 리스트"(파일명/파라미터명을 굵은 모노스페이스 + 옆에 상태칩 + 아래 설명, 구분선으로 분리) + 옆이나 아래에 **다크 코드 패널**(코드·명령어 — 밝은 배경 대신 근흑색 `#17171c` 배경, 흰/회색 텍스트).
- **필수/선택 태그**: Toss는 색 배경 없이 굵은 색 텍스트만 쓴다(`필수`=주황, 옆에 `· string`처럼 회색으로 타입). 우리 상태칩(§1)은 배경까지 쓰지만 이 "이름 굵게 + 옆에 작은 태그 + 아래 설명 한 줄, 구분선" 리듬은 그대로 가져온다.
- **버튼**: 옅은 blue 배경 + blue 텍스트의 pill 버튼(Toss `#3182F6` 계열) — 우리 팔레트의 `blue`/`blue-1`로 대체.
- **다이어그램·표를 아끼지 않는다.** 텍스트로 풀던 것(아키텍처 설명, Task 순서, 프로젝트 비교)은 최대한 Mermaid 다이어그램이나 표로 바꾼다. 산문은 각 블록의 "한 줄 설명"에만 남긴다.

### Mermaid 사용법 (고정)

```html
<pre class="mermaid">
graph LR
  A[요청] --> B[필터]
  B --> C[(Redis)]
</pre>
<script type="module">
  import mermaid from 'https://cdn.jsdelivr.net/npm/mermaid@11.17.2/dist/mermaid.esm.min.mjs';  // 버전 고정 — 실제 초기화 코드는 template.html
  mermaid.initialize({ startOnLoad: true });
</script>
```

**그릴지 말지는 SKILL.md 규칙 15의 표로 정한다**(처리 단계 3개 이상 → flow, 주체 둘 이상의 주고받기 → sequence, 구성요소 연결 → flowchart LR …). 예전 문구 "글로 설명 가능하면 굳이 다이어그램 금지, 1~2개 정도"는 삭제했다 — 에이전트가 이걸 근거로 6단계 처리 흐름을 번호 목록으로만 쓰고, 사용자가 말해야 그렸다(2026-09-23). 남발 방지 기준은 두 가지만 남긴다: 두 단계짜리 관계는 문장 하나로, 독자가 직접 따라 할 절차(명령 실행·재시작)는 번호 목록으로.

### 다이어그램 종류 다양화 (전부 flowchart TD로 밑으로만 떨어뜨리지 않기)

`wikidocs.net/287760`에서 mermaid가 지원하는 다이어그램 종류를 확인. 내용에 맞는 종류를 고른다 — 전부 flowchart는 아니다.

| 보여줄 것 | 다이어그램 | 이 프로젝트 예 |
|---|---|---|
| **가지 없는 순서 흐름**(A→B→C…) | **` ```flow `** (Mermaid 아님 — 아래 "순서 흐름은 flow 카드로") | 요청 처리 단계, 온보딩 절차 |
| 구조·아키텍처(공간적 관계) | `flowchart`(**LR 기본** — TD는 세로로만 쌓여 "쭉 떨어지는" 느낌을 만든다, 진짜 순차 단계일 때만 TD) | 세션 저장 위치 전환 |
| 시간 순서로 여러 주체가 주고받는 상호작용 | `sequenceDiagram` | 요청→필터→Redis 왕복 |
| 일정·기간·의존관계 | `gantt` | Task1~6 일정 |
| 상태 전이 | `stateDiagram-v2` | 세션 상태(로컬↔Redis) |
| 비율·구성 | `pie` | 결함 심각도 비율 |
| 브랜치 전략 | `gitGraph` | 개인브랜치→MR→stg-v2 |
| 모듈/클래스 의존관계 | `classDiagram` | base↔소비war 의존 |

**★버그·수정①: sequenceDiagram의 actor/note rect가 CSS 대신 mermaid 기본색을 그대로 보여줄 수 있다.** 사용자 실제 브라우저(시크릿모드까지 포함, 캐시 요인 배제됨)에서 재현: `<rect class="actor" fill="#eaeaea" stroke="#666">`처럼 mermaid가 액터 박스에 프레젠테이션 속성으로 자체 기본색을 직접 굽는데, 우리 `themeCSS`의 스타일시트 규칙(스펙상 프레젠테이션 속성보다 항상 우선해야 함)이 그 환경에서 이겨야 정상인데 안 이겼다. **원인은 특정 못함**(mermaid@11.17.2로 버전 고정까지 했는데도 재현 — 처음 세운 "CDN 버전 드리프트" 가설은 틀렸다). **조치**: CSS 캐스케이드에 기대지 않는다. `mermaid.run()` 완료 직후 JS로 fill·stroke·stroke-width를 **`style.setProperty(...,'important')`와 `setAttribute(...)` 둘 다** 강제로 못박는다(코드는 `template.html`의 `renderDiagrams` 함수, `mermaid.run` 호출 바로 다음, `setBoth` 헬퍼). inline style만으론 부족해서(그것도 씹힌 사례가 실제로 나옴) XML 프레젠테이션 속성 자체까지 덮어써야 CSS를 통째로 무시하는 렌더러에서도 값이 맞다. [검증 2026-09-23 · 사용자 실제 브라우저 DOM 덤프로 최종 확인 — `fill="#cfe8f3"` 속성값 자체가 바뀐 것까지 확인됨]
**예외 — 상태 다이어그램의 시작(●)·끝(◉) 점은 강제 색칠에서 뺀다.** 모든 `.node` 도형을 노드 채움색으로 덮으면 시작 점이 옅은 파랑이 되고, 끝 점의 바깥 고리와 안쪽 점이 같은 색이 되어 과녁 모양이 사라진다. `renderDiagrams`의 노드 루프가 id가 `_start-숫자`/`_end-숫자`로 끝나는 노드를 건너뛰어 mermaid 기본색(`lineColor`)을 유지한다. [검증 2026-09-23 · 내장브라우저 실측 — 수정 전 시작·끝 점 fill 모두 #cfe8f3, 수정 후 시작 #9d9da6·끝 바깥/안쪽 구분, 일반 노드·시퀀스 actor/note 색은 변화 없음]

**★버그·수정②: actor/note에 그림자(filter)를 걸 때 셀렉터를 `rect.actor`/`rect.note`로 태그까지 명시해야 한다.** bare `.actor`/`.note`는 라벨 `<text class="actor actor-box">`에도 붙어있어서, 거기 `filter: drop-shadow(...)`가 걸리면 텍스트가 겹쳐 보이는 버그가 재현된다(2026-09-22 최초 발견 당시엔 "actor/note는 그림자 자체를 포기"로 회피했는데, **회피가 아니라 셀렉터 스코프 문제였다** — 태그를 명시하니 그림자도 정상, 텍스트도 안 깨짐). `fill`/`stroke`는 원래도 안전했다(자식 `<tspan>`이 자기 `fill:#332d2f;stroke:none`을 따로 갖고 있어서 부모 텍스트 요소에 뭘 설정해도 실제로 그려지는 글자색엔 영향 없음) — 문제는 오직 `filter`뿐이었다. [검증 2026-09-23 · 내장브라우저 실측 — `.actor`에 filter 걸면 글자 겹침 재현, `rect.actor`로 좁히면 정상]

**★버그·수정③: flowchart 노드 라벨만 `font-weight:700`이 걸려있고 sequenceDiagram의 actor·message·note 텍스트는 안 걸려서 같은 문서 안에서 굵기가 안 맞았다.** `.node .label, .nodeLabel`엔 있는데 대응하는 sequence 쪽 셀렉터가 themeCSS에 없었던 누락. **조치**: `text.actor, .messageText, .noteText, .labelText, .loopText { font-weight: 700 !important; }` 추가(②의 filter 겹침 버그와 달리 `font-weight`는 텍스트 자체 속성이라 `rect.actor`로 좁힐 필요 없이 `text.actor`로 바로 지정해도 안전). [검증 2026-09-23 · 내장브라우저 실측 · 렌더 후 스크린샷으로 actor/message/note 전부 굵게 확인]

**flowchart·sequenceDiagram·stateDiagram-v2·gantt는 Pretendard+한글 정상 렌더링.** [검증 2026-09-22 · 내장브라우저 실측]

**★버그·수정: `useMaxWidth`(mermaid 기본값 true)가 브루탈리스트 그림자·굵은선을 지운다.** mermaid는 기본적으로 SVG를 컨테이너 폭에 맞춰 축소한다(viewBox는 원본 노드 크기 그대로, `width:100%`+`max-width`로 시각적 크기만 줄임). 이때 `filter: drop-shadow(4px 4px ...)`·`stroke-width: 2.5px` 같은 값은 SVG 사용자 단위라 **똑같이 축소돼**, 노드 많은 가로형 flowchart(예: 6노드 LR, viewBox 1390px→818px 컨테이너, 0.588배)에서는 그림자가 사실상 안 보이는 크기까지 쪼그라든다. 반대로 컨테이너 폭과 viewBox가 비슷한 다이어그램(예: 0.988배)은 정상으로 보여서 **다이어그램마다 결과가 달라 보였다** — 이게 최초 검증([검증 2026-09-22])이 놓친 부분이다. `getComputedStyle`로는 `filter` 값이 정확히 잡히는데도 실제 스크린샷엔 안 보여서 "CSS는 맞는데 왜 안 보이지" 함정에 빠지기 쉽다. **조치**: `template.html`의 `mermaid.initialize`에 `flowchart: { useMaxWidth: false }, sequence: { useMaxWidth: false }, gantt: { useMaxWidth: false }, state: { useMaxWidth: false }` 추가 — 다이어그램을 원본 크기로 그리고, 컨테이너보다 넓으면 `pre.mermaid`의 기존 `overflow-x:auto`로 가로 스크롤시킨다(줄여서 감추는 대신 스크롤로 보여주는 쪽). ### 브루탈리스트 스타일 (색은 우리 팔레트, 굵은 테두리+그림자는 참고)

출처: `modern-mermaid.live`(MIT, `gotoailab/modern_mermaid`)의 Brutalist 테마 CSS. **실제 초기화 코드의 진실은 `template.html`**(다크모드 분기 포함) — 아래 블록은 개념 설명용. 원본은 장식색을 `nth-child`로 무작위 순환시키지만, 우리는 그 대신 **§1 색언어(성공=초록/실패=빨강/진행중=파랑/중립=회색)를 mermaid `classDef`로 직접 지정**한다(장식이 아니라 의미).

    }
    .node .label, .nodeLabel { font-weight: 700 !important; }

```

색을 상태별로 쓸 땐 다이어그램 소스에서 **클래스 이름만** 붙인다(hex는 템플릿이 라이트/다크에 맞게 칠함 — §9 v2.1):

### v2.2 (2026-09-23) — 라이트 기본, 다크는 선택

라이트를 선호하는 독자가 많아서, 보는 사람 OS가 다크여도 문서는 라이트로 연다. 다크는 원하는 사람만 켠다.

- **기본 = 라이트 고정.** `prefers-color-scheme` 자동 전환을 없애고 `<html data-theme>`로만 결정한다. head의 짧은 스크립트가 본문 그리기 전에 정해서 깜빡임이 없다.
- **라이트 톤 = 흰 종이.** 토스 개발자문서·우아한형제들/토스 기술블로그(§6·§7) 관찰대로, 읽는 문서는 흰 바탕(`--bg #fff`) + 얇은 선(`--line #e6e8ec`) 구분. 옅은 회색(`--surface-2 #f7f8fa`)은 근거 박스·캡처 카드·표 머리에만. 그림자는 거의 안 보일 정도로. 코드 패널만 어둡게(토스 문서와 같은 방식).
- **다크 = 선택.** 상단 바 오른쪽 둥근 아이콘 버튼 — 라이트일 땐 달(누르면 다크), 다크일 땐 해(누르면 라이트). 아이콘뿐이라 뜻은 `aria-label`·`title`("다크 모드로 바꾸기")로 전달. 고른 값은 `localStorage`(`hrr-theme`)에 남아 다음 보고서에도 적용된다. 바꾸면 Mermaid도 새 색으로 다시 그린다.
- **문서별 기본값.** frontmatter `theme: light`(기본) | `dark` | `auto`(보는 사람 OS 따름). 보는 사람이 토글로 고른 값이 항상 우선.
- **요약 박스는 흰 종이 위에서 한눈에.** 옅은 파랑 바탕(`--blue-1` 60%) + 굵은 파랑 왼쪽 선(5px) + 채운 "요약" 배지(`--blue-7` 바탕, 자기 줄) + 본문보다 큰 글자(1.08em, 500). 당근·카카오뱅크의 "좌측 컬러보더 요약 박스"(§7 2차)를 라이트 톤에 맞춘 것. 이전 버전은 `border` 단축속성이 `border-left` 뒤에 와서 왼쪽 선이 회색으로 덮여 있었다 — 순서 주의.
- **인쇄는 항상 라이트.** 다크로 보고 있어도 인쇄 스타일이 라이트 토큰으로 되돌린다.

OS 다크 + 저장값 없음 → 라이트로 열림. 토글 → 다크 전환, 다이어그램 다크 색으로 다시 그림, 새로고침 후에도 유지. 다시 토글 → 라이트. `theme: auto`는 OS 다크면 다크, 라이트면 라이트. [검증 2026-09-23 · 내장브라우저 실측(JS 계산값 + 라이트·다크 스크린샷, 아이콘 전환·요약 박스 포함)]

**★버그·수정④: 라이트 모드 `--line`(#e6e8ec, 흰 배경 대비 1.23:1)이 너무 옅어서 `.block`(섹션 카드)·표·근거박스 테두리가 흰 바탕에 묻혀 안 보였다.** "얇은 선" 컨셉(§9 v2.2, 토스 개발자문서 관찰)을 과하게 적용한 결과. **조치**: `#d1d5db`(Tailwind gray-300, 흰 배경 대비 1.47:1 — "옅지만 보이는" 테두리)로 교체. 참고로 이 값도 WCAG 1.4.11의 3:1에는 못 미친다. 3:1은 이해에 꼭 필요한 UI·그래픽 요소 기준이라 장식용 카드 테두리엔 적용되지 않고, 카드 구분은 여백·배경이 함께 한다. 입력칸처럼 테두리가 곧 경계인 요소를 만들면 3:1(예: #949494 = 3.03:1) 이상을 쓴다 — `template.html`의 `:root` 라이트 토큰과 `@media print` 강제 라이트 토큰 둘 다. ### v2.3 (2026-09-23) — 순서 흐름은 flow 카드로, 흐름도는 역할 색으로

**순서 흐름은 ` ```flow ` 카드로 그린다.** Mermaid(dagre 자동 배치)는 가지 없는 흐름을 폭과 상관없이 항상 한 줄로 늘어놓고, 폭 기준 줄바꿈 기능이 없다. 서브그래프로 S자를 만드는 방법도 불안정하다 — 서브그래프 안 노드가 바깥과 연결되면 Mermaid가 그 서브그래프의 방향 설정을 무시한다. 그래서 가지 없는 흐름은 렌더러 자체 부품으로 그린다: 카드가 화면 폭에 맞춰 줄바꿈되고, 같은 줄은 가로 화살표, 줄이 바뀌는 곳은 앞 카드 아래에서 다음 카드 위로 곡선(S자)으로 잇는다. 좁은 화면에선 한 줄에 하나씩 세로로 쌓인다. 가지·합류·반복이 있으면 Mermaid를 쓴다.

```
```flow
제휴사 요청 | 외부에서 API 호출 | ext
컨트롤러 | 파라미터 추출 | entry
공통 서비스 | 제휴사 등록 확인, 키 검증 | logic
DB 테이블 | 입과·진도 반영 | data
```
```

한 줄 = 한 단계, `제목 | 설명 | 역할` (설명·역할 생략 가능). 번호(01, 02…)는 자동.

**흐름도·구조도는 역할 색을 쓴다.** 색은 여전히 의미를 나타낼 때만 쓴다. 상태가 없는 흐름도가 전부 같은 파랑으로 나오던 건 설계 의도였지만, 흐름도에선 "역할"도 의미다. 역할 색 4개는 상태 색(초록·빨강·주황·노랑)과 겹치지 않게 골랐다: `ext` 외부 주체(분홍) · `entry` 진입점—컨트롤러·API·화면(연보라) · `logic` 처리—서비스·배치(하늘) · `data` 데이터—쿼리·DB·저장소(청록). Mermaid에선 `class A ext`, flow 카드에선 세 번째 칸. **한 다이어그램 안에서는 역할 색과 상태 색(done/fail/…) 중 하나만 쓴다** — 섞으면 "분홍이 외부인지 경고인지" 헷갈린다. 라이트·다크 두 벌이 템플릿 토큰(`--role-*`)과 Mermaid `fill`·2차 방어 코드(`stateFill`)에 같이 들어 있다.

### v2.4 (2026-09-23) — 카드 두 종류: 숫자 카드·항목 카드

무료 템플릿·컴포넌트 사이트를 직접 열어 보고, 보고서 구조에 맞는 것만 골랐다.

**숫자 카드 ```stats** — 한 줄 = `라벨 | 값 | 보조 설명 | 상태`. 상태가 왼쪽 색 띠와 라벨 색을 정한다(완료 초록·실패 빨강·주의 주황·미검증 노랑·중립 회색·기본 파랑). 규칙 6의 "수치가 곧 결론"을 요약 바로 아래에 모아 보여 줄 때 쓴다. 2~4개가 알맞다.

**항목 카드 ```cards** — 빈 줄로 카드를 나누고, 첫 줄은 제목(`[완료]`·`[주의]` 태그 가능), 나머지는 본문(문장·불릿·`근거:` 줄). 한 줄에 놓인 카드는 높이가 같다. 선택지 비교에선 고른 쪽 제목에 `[추천]` — 파란 테두리와 채운 배지로 강조된다. 항목마다 같은 짧은 속성만 있으면 카드 말고 표.

````
```stats
불일치 | 0건 | 가이드와 소스가 모두 일치 | 완료
확인 못 한 항목 | 2개 | 운영 DB 권한 필요 | 미검증
```

```cards
표준 공통 모듈 [추천]
코드 수정 없이 DB 등록만으로 붙입니다.
- 기간: 1일

커스텀 모듈
제휴사 요구에 맞춰 코드를 새로 만듭니다.
- 기간: 1~2주
```
````

**배치는 본문 길이와 카드 수로 자동 결정** — 실제 문서(제휴사 가이드 "놓치기 쉬운 3가지", 본문 80~220자 + 근거 줄)를 3열에 넣었더니 카드 폭이 276px라 문장이 서너 줄로 쪼개지고, 근거 파일명이 중간에서 잘리고(`selectPartnerKey`, `SYNC_DONE_ YN`), 제목이 긴 카드만 배지가 따로 한 줄을 차지하고, 짧은 카드 아래가 비었다. 카드는 원래 짧은 내용용이다.

| 조건 | 배치 |
|---|---|
| 본문(근거 줄 뺀 글자 수) 60자 이하 | `grid` — 카드 4개 이하면 개수만큼 열, 그 이상은 4 또는 3열 |

| 140자 초과, 또는 half인데 카드 수 홀수, 또는 카드 1개 | `wide` — 한 줄에 하나. 왼쪽 30%에 번호·배지·제목, 오른쪽에 본문 |
