# Before / after — 실패 모드별 12쌍

같은 사실, 다른 문장. 왼쪽은 에이전트가 기본으로 쓰는 것, 오른쪽은 이 스킬을 지킨 것.
규칙 번호는 `SKILL.md`.

## 1. 단편 불릿 → 온전한 문장 (규칙 4)

**Before**
```
- A · 시간축 · render+send 스킵
- B · 이벤트 기반 · diff만
- 메모리 ↓, 지연 ↑
```

**After**
```
- 방법 A는 시간 간격마다 확인하다가 바뀐 게 없으면 다시 그리지 않습니다.
- 방법 B는 값이 바뀔 때만 움직이고, 바뀐 부분만 보냅니다.
- 그래서 B가 메모리는 덜 쓰지만 첫 반응은 조금 늦습니다.
```

## 2. 본문 속 코드 위치 → 근거 메모 (규칙 6)

**Before**
```
세션 만료가 `SessionConfig.java:41`에서 30분으로 고정돼 있고 `application.yml:88`의 값을 무시합니다.
```

**After**
```
세션 만료 시간이 설정 파일 값과 상관없이 30분으로 고정돼 있습니다.
설정을 바꿔도 반영이 안 되는 이유가 이것입니다.

근거: `SessionConfig.java:41`, `application.yml:88`
```

## 3. 자작 용어 → 평이한 풀이 (규칙 5)

**Before**
```
Shadow-Sync 레이어가 dual-write 윈도우 동안 drift를 흡수합니다.
```

**After**
```
전환 기간에는 옛 저장소와 새 저장소 양쪽에 같이 씁니다.
그 사이 두 쪽 값이 어긋나면 새 저장소 값을 기준으로 맞춥니다.
```
("Shadow-Sync"는 우리가 붙인 이름이라 독자는 모른다. 이름을 쓰려면 먼저 이렇게 풀고, 그 다음에 "이걸 이 문서에선 Shadow-Sync라고 부르겠다"로 도입한다.)

## 4. 수식 → 말 (규칙 5)

**Before**

**After**

항목 1만 개면 느린 요청 기준으로 4.2초가 걸립니다.

## 5. 얼버무리는 서두 삭제 (규칙 8)

아래 내용은 참고용이며 실제 적용 전 검토가 필요합니다.
결론부터 말씀드리면, 배치가 느린 원인은 인덱스 누락이었습니다.

## 8. 요약 박스 압축 (규칙 2)

```

**After**
```
> 로그인 세션을 서버 메모리에서 Redis로 옮겼습니다.
> 개발 환경 검증은 끝났습니다.
> 운영 반영 시점만 정하면 됩니다.
```
(무엇을 / 지금 상태 / 결정할 것. 비유는 요약 박스에 넣지 않는다. 제목 반복, "상세하고 체계적으로" 같은 겹수식어는 삭제.)

## 9. 배경: 이야기 → 요청 분석 (규칙 13)

**Before** — 시간순으로 풀고, 비유로 시작하고, 요청이 무엇이었는지는 안 나옴
```
## 배경

지금까지 세션은 각 서버의 메모리에만 있었습니다.
비유하자면 출입증을 경비실 한 곳에만 보관하는 것이라, 그 경비실이 문을 닫으면 모두가 다시 신분 확인을 받아야 했습니다.
그래서 이번에 Redis라는 공용 보관함으로 옮기게 되었습니다.
```

**After** — 실제 요청을 정확히 다시 쓰고, 현상·원인·조건·범위·판단 기준으로 나눔
```
## 배경

- **요청** — 운영팀이 배포 뒤에도 사용자 로그인이 유지되게 해 달라고 요청했습니다(9/15 운영 회의).
- **현상** — 서버를 재시작하면 그 서버에 붙어 있던 사용자가 모두 로그아웃됩니다. 지난달 배포 6회에서 매번 발생했습니다.
- **원인** — 세션을 각 서버 메모리에만 저장해서, 서버가 내려가면 세션도 함께 사라집니다.
- **요구사항** — 재시작이나 서버 교체 뒤에도 세션이 유지되어야 하고, 만료 시간 30분은 그대로여야 합니다.
- **범위 밖** — 동시 로그인 정책은 이번 작업에서 바꾸지 않습니다.
- **판단 기준** — 서버 한 대를 재시작해도, 로그인한 사용자의 다음 요청이 정상 응답하면 성공입니다.
```
(수치와 출처는 실제 요청·로그·티켓에서 가져온다. 모르면 `[미검증]`을 붙이고 지어내지 않는다. 비유가 꼭 필요하면 원인 줄 옆에 한 구절로만.)

## 10. 번역투 한국어 → 자연스러운 한국어 (규칙 14)

실제로 나온 문서(제휴사 공통 인터페이스 가이드)의 첫 섹션.

**Before**
```
## 요청이 지나가는 길

이 구조는 자판기와 같습니다.
기계(코드)는 하나뿐이고, 안에 채워 넣는 상품 목록(DB 설정값)만 회사마다 다릅니다.
요청은 딱 세 단계를 지나갑니다.
먼저 컨트롤러가 요청을 받아 업체코드·연동ID·모듈코드를 뽑아냅니다.
그다음 서비스 두 개가 각각 "이 요청이 진짜 등록된 제휴사가 보낸 게 맞는지" 확인하고, 암호화된 데이터를 풀고, 응답 데이터를 다시 조립합니다.
역할을 나누면 이렇습니다.
```

**After**
```
## 요청 처리 흐름 — 코드는 공통, 제휴사별 차이는 DB 등록값이 결정

모든 제휴사의 요청은 같은 코드로 처리되며, 제휴사마다 다른 부분은 DB에 등록한 설정값으로만 나뉩니다.
처리는 세 단계입니다.

1. 컨트롤러가 요청에서 업체코드·연동ID·모듈코드를 추출해 서비스로 넘깁니다.
2. 서비스가 등록된 제휴사인지와 인증키 유효 여부를 확인한 뒤, 데이터를 복호화해 저장하거나 조회 결과로 응답을 구성합니다.
3. 쿼리 XML에 정의된 SQL이 테이블을 조회·저장합니다.
```
(이 예시는 문장만 고친 것이다. 실제 문서에서는 이 세 단계도 규칙 15에 따라 ` ```flow ` 그림으로 바꾼다 — 11번 참고.)

| Before | After | 이유 |
|---|---|---|
| 요청이 지나가는 길 | 요청 처리 흐름 | 요청을 사람처럼 쓴 은유, 영어 "the path a request takes"를 옮긴 번역투 |
| 자판기 비유 + 괄호 풀이 | 첫 문장에 사실을 바로 씀 | 비유를 괄호로 다시 풀면 두 번 읽어야 함 |
| 딱 세 단계를 지나갑니다 | 처리는 세 단계입니다 | 구어체 "딱", 의인화 "지나가다" |
| 뽑아냅니다 / 조립합니다 | 추출합니다 / 구성합니다 | 번역투 동사 |
| 서비스 두 개가 각각 A·B·C | 단계별로 나눠서 씀 | 두 서비스는 하는 일이 달라서 "각각"이 사실과 어긋남 |
| 역할을 나누면 이렇습니다. | (삭제) | 내용 없이 다음 표만 예고하는 문장 |

## 11. 번호 목록으로만 쓴 처리 흐름 → 그림 (규칙 15)

**Before** — 누가 무엇을 하는지 순서가 핵심인데 글로만 나열
```
## 요청 처리 흐름

1. 제휴사가 공개키 발급 API를 호출합니다.
2. 컨트롤러가 업체코드·연동ID·모듈코드를 추출합니다.
3. 공통 서비스가 등록된 제휴사인지 확인합니다.
4. 업체별 서비스가 데이터를 복호화합니다.
5. 쿼리 XML의 SQL이 테이블에 저장합니다.
6. 배치가 10분 주기로 실제 테이블에 반영합니다.
```

**After** — 요지 한 문장 + 흐름 그림 (단계 설명은 카드 안으로)
````
## 요청 처리 흐름

제휴사 요청은 컨트롤러·서비스 2개·쿼리를 거쳐 저장되고, 배치가 10분마다 반영합니다.

```flow
제휴사 | 공개키 발급 API 호출 | ext
컨트롤러 | 업체코드·연동ID·모듈코드 추출 | entry
공통 서비스 | 등록된 제휴사인지 확인 | logic
업체별 서비스 | 데이터 복호화 | logic
쿼리 XML | 테이블에 저장 | data
배치 | 10분 주기로 실제 테이블 반영 | data
```
````
(주어가 있는 처리 단계가 3개 넘게 이어지면 그림 후보. 반대로 "환경변수를 넣습니다 → 서버를 재시작합니다"처럼 독자가 따라 할 절차는 번호 목록 그대로 둔다.)

## 12. 업무 관용투·용어 섞임 → 담백한 한국어 (규칙 14)

번역투가 아니라 한국 업무 문서에서 온 습관이다. 한국어로 직접 쓴 API 문서 221건에 번역판 28건보다 오히려 많았다(해당 42% / 32%, 하시기 바랍니다 20% / 4%). 그래서 번역투만 보는 검사로는 잡히지 않는다.

**Before**
```
해당 API 호출 시 에러가 발생하는 경우, 해당 오류 코드에 대한 내용을 확인하시기 바랍니다.
토큰 갱신을 진행하기 위해서는 리프레시 토큰을 가지고 있어야 하며, 갱신된 토큰은 인증 서버에 의해 반환됩니다.
재시도는 최대 3회까지 수행하는 것이 가능합니다.
```

**After**
```
주문 조회 API가 오류를 반환하면 오류 코드 표에서 원인을 확인해 주세요.
토큰을 갱신하려면 리프레시 토큰이 있어야 하고, 인증 서버가 새 토큰을 반환합니다.
재시도는 3회까지 할 수 있습니다.
```

| Before | After | 이유 |
|---|---|---|
| 해당 API / 해당 오류 코드 | 주문 조회 API / 오류 코드 표 | "해당"은 가리키는 대상을 독자가 되짚게 함. 실제 이름을 쓴다 |
| 에러가 … 오류 코드 | 오류 … 오류 코드 | 한 문서에 같은 개념 두 단어. 권장어는 references/ko-terms.md |
| 오류 코드에 대한 내용을 확인 | 오류 코드 표에서 원인을 확인 | "에 대한 내용"은 빈말. 무엇을 확인하는지 바로 씀 |
| 확인하시기 바랍니다 | 확인해 주세요 | 공문서 어미. 같은 정중함을 짧게 |
| 갱신을 진행하기 위해서는 | 갱신하려면 | 명사+진행 대신 동사, "위해서는"은 to-부정사 번역투 |
| 리프레시 토큰을 가지고 있어야 | 리프레시 토큰이 있어야 | have를 옮긴 "가지다" |
| 인증 서버에 의해 반환됩니다 | 인증 서버가 반환합니다 | 행위자를 주어로, 능동형 |
| 수행하는 것이 가능합니다 | 할 수 있습니다 | "수행"과 "것이 가능" 둘 다 군더더기 |

# 같은 발견, 독자가 다르면 (규칙 1)

발견: "세션 만료가 설정과 무관하게 30분 고정. 원인은 `SessionConfig.java:41`의 하드코딩."

| 독자 (`audience:`) | 어떻게 달라지는가 | 그 독자용 첫 문장 |
|---|---|---|
| `team` — 같은 팀 개발자 | 용어 그대로, 배경 생략, 코드 위치는 근거 메모에 | 세션 만료가 30분 하드코딩이라 `application.yml` 값이 무시됩니다. |
| `cross-team` — 타팀·기획 | 용어 전부 풀이, "그래서 뭐가 달라지나" 중심, 코드 언급 없음 | 로그인 유지 시간을 설정으로 바꿔도 실제로는 항상 30분입니다. |
| `leadership` — 리더·경영 | 한 페이지, 결정 사항과 리스크만, 다이어그램 최대 1개 | 로그인 유지 시간 설정이 동작하지 않고 있으며, 고치는 데 반나절이면 됩니다. 반영 시점 결정이 필요합니다. |
| `external` — 외부 공유 | 위 `cross-team` 톤 + 브랜치명·서버명·사번·내부 파일 경로 제거 (lint가 잡음) | 로그인 유지 시간이 설정값과 다르게 동작하는 문제를 확인했고 수정 중입니다. |
