# 한국어 기술 용어·표현 기준 (규칙 14)

보고서에서 같은 개념은 아래 권장어 하나로 쓴다.
기준은 사전 순화어가 아니라 **한국 개발 문서가 실제로 쓰는 말**이다 — 보고서 독자가 개발팀이라 그쪽이 잘 읽힌다.
영어 원어는 문서에서 처음 나올 때 한 번만 괄호로 병기한다.

근거: 한국어 API 문서 249건 조사(2026-10-01).
한국어로 직접 쓴 문서 221건(네이버·카카오·토스·쿠팡·NHN Cloud·공공데이터포털·한국은행 등 48곳)과
해외 문서의 한국어 번역판 28건(Google·AWS·Microsoft·GitHub 등 9곳)을 같은 기록 형식으로 비교했다.
아래 "N건"은 그 단어를 쓴 한국어 원문 문서 수.

## 2. 고칠 표현 — 두 묶음

출처가 다르다.
번역투는 영어 문장 구조에서 와서 번역판에 몇 배 많고, 업무 관용투는 한국 업무 문서 습관이라 한국어 원문에 오히려 더 많다.
괄호 안은 그 표현이 한 번이라도 나온 문서 비율(한국어 원문 / 번역판).

### 번역투

| 표현 | 비율 | 고치는 방향 |
|---|---|---|
| 사물 주어 + 허용·요구 | 20% / 71% | "이 API는 인증을 요구합니다" → "이 API를 호출하려면 인증해야 합니다" |
| 에 의해 ~됩니다 | 3% / 29% | "인증 서버에 의해 발급됩니다" → "인증 서버가 발급합니다" |
| 에 대한 | 40% / 79% | "결제 취소에 대한 처리 방법" → "결제 취소 방법", "과정에 대해 안내합니다" → "과정을 안내합니다" |
| 로 인해 | 10% / 32% | "타임아웃으로 인해 실패" → "타임아웃 때문에 실패" |
| 를 통해 ~할 수 있습니다 | 35% / 50% | "웹훅을 통해 상태 변경을 수신할 수 있습니다" → "상태가 바뀌면 웹훅으로 알려 줍니다" |
| 하기 위해서는 | — | "갱신하기 위해서는 ~이 필요합니다" → "갱신하려면 ~이 있어야 합니다" |
| 을 가지다 (have) | 3% / 11% | "권한을 가진 사용자" → "권한이 있는 사용자" |
| 선택적 (optional) | 0% / 32% | "선택적 파라미터" → "선택 파라미터" |
| 자동 조사 | 번역판에만 | "을(를)", "(으)로" → 받침에 맞는 조사 하나 |

### 업무 관용투

| 표현 | 비율 | 고치는 방향 |
|---|---|---|
| 해당 ~ | 42% / 32% | "해당 오류가 나면" → "이 오류가 나면", 또는 실제 이름 |
| 하시기 바랍니다·부탁드립니다 | 20% / 4% | "문의하시기 바랍니다" → "문의해 주세요" |
| 을 진행/수행합니다 | 12% / 0% (진행) | "검증을 진행합니다" → "검증합니다" |
| 하는 것이 가능합니다 | 5% / 0% | "조회하는 것이 가능합니다" → "조회할 수 있습니다" |
| 하도록 하겠습니다 | 4% / 0% | "확인하도록 하겠습니다" → "확인하겠습니다" |

## 3. 끝맺음

- 본문은 합니다체(한국어 원문 70%).
- 표 설명 칸은 명사구로 끝내고 조건·기본값은 괄호에 넣는다: "한 페이지 결과 수(기본값 10)" (한국어 원문 63%, 번역판 11% — 번역판은 칸마다 "~입니다" 문장).
- 독자에게 할 일을 말할 때는 "~해 주세요" 하나로 맞춘다. "하시기 바랍니다", "하십시오", "참고합니다"를 한 문서에서 섞지 않는다.

## 4. 확인 수준 — 한 말보다 강하게 쓰지 않는다

작업 보고서에서 가장 비싼 실수는 동사 선택에서 난다.
한 일보다 센 동사를 고르면 독자는 끝난 일로 읽는다.

| 표현 | 쓰려면 있어야 하는 것 | 넓히면 안 되는 것 |
|---|---|---|
| 관찰했다 | 어떤 화면·로그·표본에서 본 것 | 관찰 → 원인 확정 |
| 추정한다 | 그렇게 본 이유와 아직 배제하지 못한 설명 | 추정 → 확인 |
| 확인했다 | 대상·자료·방법·범위 | 로그인 성공 → 권한 검증 |
| 검증했다 | 기준·시험 조건·결과 | 개발 환경 시험 → 운영 검증 |
| 완료했다 | 약속한 완료 기준을 채운 것 | 코드 수정 → 배포까지 완료 |

- 원문·근거에 있는 당위("~해야 한다"), 추측("~일 수 있다"), `[미검증]`은 윤문하면서 지우거나 단정으로 바꾸지 않는다. 지울 것은 근거 없이 붙인 유보뿐이다.
- 반대로 원문에 없던 유보·한계·권고를 새로 붙이지도 않는다. "정확하게 다듬어 달라"는 요청에서 모델이 근거 없는 한정 표현을 덧붙인다는 보고가 있다(LIAO-2026 사전 인쇄본을 sepia가 요약한 것, LLM 코더 집계, 논문 원문은 미확인 — 조사 보고서 4-4절).
- 원문에 없던 "이미·반드시·기본·필수"를 더하지 않는다. "예정이다 → 한다", "기대한다 → 효과가 있다", "검토 중이다 → 결정했다"도 같은 승격이다.
- **출처 세탁 금지.** "전문가들은 효과가 크다고 말한다"에서 "전문가들은"만 지우면 남의 말이 사실이 된다. 보고서에서는 출처를 쓰거나, 주장 전체에 `[미확인]`을 달거나, 중요하지 않으면 주장째 뺀다. 윤문만 할 때는 문장을 그대로 두고 `확인할 점`에 "출처 필요"를 적는다(유보를 새로 달지 않는 규칙과 맞춘다).
- 이 표는 한 줄짜리 순위가 아니다. 대상이 다르면 "관찰 기록 작성 완료, 동작 검증 미실시"가 정상 상태다.

출처: 보고서 검증 단계의 확인 수준 구분, im-not-ai의 서법 보존 원칙(v2.4), no-ai-slop-ko(MIT)의 주장 강도·출처 경계.

## 5. lint가 잡는 것

- 경고: 에 의해, 되어지다, 하기 위해서는, 선택적 + 명사, 을 가진/가지는, 자동 조사, 하시기 바랍니다·부탁드립니다, 하는 것이 가능, 하도록 하겠습니다, 을 진행/수행합니다, 파라메터, 어플리케이션, 용어 섞임(오류/에러, 반환/리턴, 파라미터/매개변수).
- 경고(공손 중첩): "~드릴 수 있도록 하겠습니다", "~주시면 감사드리겠습니다", "~드리고자 합니다". 예의는 두고 단계만 줄인다: "공유드리겠습니다", "확인해 주세요", "안내드립니다".
- 힌트: 사물 주어 + 허용·요구, 영어 낱말 + 하다("Open 하시면"), 해당·에 대한·를 통해·로 인해가 한 문서에 4번 이상.
- 힌트(한국어 AI 문형, 에세이·위키 코퍼스 측정): 부정 대구 "A가 아니라 B" 2번 이상, "~하는 이유다", 분열문 "핵심은 ~이다" 2번 이상, "단순한 X를 넘어".
- 힌트(마무리 틀, 1번부터): 문장 첫머리 "결론적으로·요컨대·종합하면·요약하자면·한마디로", "시사하는 바가 크다", "~할 때입니다·시점입니다". 출처: im-not-ai 분류 D-1·D-2·D-6, linkedin-agent-skill li-human의 "in summary" 틀.
- 힌트(Claude 버릇, 1번부터): 이모지(제목·문장, ↔·★·✓ 같은 글자 모양 기호는 제외), 본질 단정 "X는 결국 Y입니다". 분열문에는 "중요한 건·필요한 건"도 센다. 근거: 날것의 Claude 글 15개(블로그·칼럼·보고서·회고·제안서·안내서·뉴스레터·발표 원고·제품 소개, 2026-10-19)에서 이모지 6개 글·결국 단정 2개 글, 이 PC 보고서 18건에서 둘 다 0번. 같은 비교에서 "~일 뿐입니다"(보고서 9건에 나옴)와 "~하는 것은 ~입니다"(6건)는 오탐이 많아 넣지 않았다.
- 힌트(한 문서에 4번 이상): 에 있어서, ~라는/다는 점에서, 와 관련하여, 이루어지다, 할 필요가 있다, 문장 첫머리 "이는"과 "즉,". 출처: im-not-ai 분류 A-3·A-4·A-5·A-12·I-4·H-3·H-4. 기술 보고서에서는 정상 용법도 흔해 횟수로만 본다. 한자어 명사화(고도화·효율화·제고·도출)도 4번부터.
- 힌트(1번부터): 의례적 도입("오늘날", "빠르게 변화하는 시대에"), 가짜 통찰 예고("주목해야 할 점은", "답은 명확합니다"), "선택이 아니라 필수", 근거 없는 중요성("중요한 역할을 합니다", "토대를 마련"), 출처 없는 권위("전문가들은", "연구에 따르면"), 마무리 틀 "궁극적으로". 출처: no-ai-slop-ko(MIT) 패턴 목록. 기술 보고서 빈도는 미측정 — 2026-11-12 이 PC 프로젝트 문서 150건에는 한 번도 나오지 않아 오탐도 측정하지 못했다.
- 경고(두 모드 공통): 보이지 않는 문자 — 폭 없는 공백, 글 중간 BOM, 방향 제어, 태그 문자. 이모지를 잇는 결합 문자는 제외. 출처: li-human의 FINGERPRINT 검사.
- 따옴표 안("…")은 남의 말(티켓 제목, 오류 메시지, 고치기 전 예문)이라 건너뛴다.

## 6. 제목·문장 습관

lint가 못 잡거나 힌트로만 알리는 것들이다. 첫 한국어 초안을 쓰기 전에 읽는다.

**제목과 알리는 문장**
- 은유·의인화 제목을 쓰지 않는다. "요청이 지나가는 길", "~의 여정", "~는 이렇게 돌아간다", "테이블 지도" → "요청 처리 흐름", "등록 테이블 목록", 또는 결론 문장.
- 알리는 문장("역할을 나누면 이렇습니다.", "정리하면 다음과 같습니다.")은 빼고 표를 바로 보인다.

**동사와 말투**
- 번역한 동사를 바꾼다. 요청이 지나가다 → 처리되다, 데이터를 조립하다 → 구성하다, 창구를 열다 → 제공하다, 뽑아내다 → 추출하다, 돌아가다 → 동작하다.
- 구어 강조어(딱, 진짜, 전부 다, 엄청)를 쓰지 않는다.
- 괄호로 푸는 비유("기계(코드)", "상품(DB 설정값)")를 쓰지 않는다. 괄호가 있어야 알아듣는 말이면 대상을 바로 부른다.
- 하는 일이 다른 대상을 한 문장으로 매끄럽게 묶지 않는다. "두 서비스가 각각 A하고 B하고 C합니다"는 문장을 나눈다.

**따옴표**
- 따옴표는 누가 말하거나 쓴 말에만, 그렇다는 표지("~라고 밝혔습니다", "~라는 제목")와 함께 쓴다.
- 강조·라벨·지어낸 말에 따옴표를 치면 비꼬거나 의심하는 말로 읽힌다("가장 큰 영향"을 보장하지 않습니다). 따옴표를 빼고, 정말 무게가 필요한 한 구절만 굵게 쓴다.
- 티켓 제목이나 고치기 전 예문은 바꿔 쓰지 말고 따옴표로 인용한다. lint는 따옴표 안을 남의 말로 보고 건너뛴다.

**AI 문형과 마무리**
- 부정 대구 "A가 아니라 B"는 독자가 실제로 믿던 것을 바로잡을 때만 쓴다.
- "~하는 이유다", 분열문 "핵심은 ~이다", "단순한 X를 넘어 Y", 본질 단정 "X는 결국 Y입니다"는 결론을 바로 말하는 문장으로 바꾼다. 고친 문장이 다른 틀(결국·이유다·아니라)을 새로 만들지 않았는지 본다.
- 마무리 틀(문장 첫머리 결론적으로·요컨대·종합하면, "시사하는 바가 크다", "~할 때입니다")은 뺀다. 결론은 요약 상자와 섹션 첫 줄에 이미 있다.
- 한 섹션에서 문장 첫머리 접속어(다만·그러나·하지만·그래서·따라서·또한·한편…)가 3개 이상이면 독자가 작성자의 추론을 따라가게 된다. 결론을 먼저 쓰고 사실을 잇는다. 접속어로 잇는 대신 앞 문장에 합친다.
- 이모지를 제목·문장에 쓰지 않는다. 상태는 확인·추정 같은 글자 라벨로 쓴다.

**목소리 지키기(윤문만·지적만)**
- 필자의 어휘, 호흡, 반말·존댓말 단계, 사투리, 유머, 망설임은 그대로 둔다. 걸리는 패턴이 있어도 사람이 쓴 강한 문장은 건드리지 않는다.
- 주어 없이도 읽히는 문장에 "저는·우리는"을 다시 넣지 않는다.
- 짧게 만드는 것과 잘 쓰는 것은 다르다. 모든 문장을 단문으로 자르지 않는다.
- 한 대상을 문단마다 다른 이름으로 바꿔 부르지 않는다(캐시 → 저장소 → 임시 보관 계층). 같은 대상이면 같은 말을 반복한다.
- 상투적 마무리를 지운 자리에 새 교훈이나 할 일을 지어 넣지 않는다. 원문의 마지막 근거 있는 문장에서 끝낸다.
